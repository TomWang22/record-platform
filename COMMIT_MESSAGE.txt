Performance Optimization, Infrastructure Improvements, and UX Enhancements

This commit includes significant performance tuning for PostgreSQL fuzzy search,
infrastructure cleanup and fixes, and user experience improvements to the shopping
cart functionality.

## Performance Optimizations

### PostgreSQL Fuzzy Search Function
- Restored `search_records_fuzzy_ids` to Nov 26 gold run specification
  - Always uses `records.records` with partial index (removed hot table branch)
  - Restored CTE structure for known-good ~17ms execution time
  - Fast mode: candidate_cap=40, min_rank=0.50 (matches gold run)
  - Deep mode: candidate_cap=150, min_rank=0.35
  - Fixed `SET search_path TO 'records', 'public', 'pg_catalog'` syntax

### PostgreSQL Benchmark Tuning
- Enhanced `run_pgbench_sweep.sh` with aggressive performance tuning
  - Added statement_timeout, lock_timeout, idle_in_transaction_session_timeout
  - Implemented deadlock_timeout for faster deadlock detection (500ms)
  - Added plan_cache_mode, join_collapse_limit, from_collapse_limit for planning optimization
  - Enforced critical settings (jit=off, synchronous_commit=off) via `enforce_critical_pgoptions()`
  - Improved wait_for_db_ready() with faster timeout and direct psql calls
  - Enhanced latency reporting with full percentile coverage (p999, p9999, p99999, p999999, p9999999, p100)
  - Added latency_cuts.txt report for cold/warm cache analysis

### Performance Regression Investigation
- Identified root cause of 8x performance regression (Nov 26 vs Nov 29)
  - Environmental issue: puddle pods causing CPU/memory contention
  - Function code was correct (matched gold run spec)
  - After cleanup: Performance should return to gold run levels

## Technical Details

### Shopping Cart Architecture
- Cross-database queries: Shopping service connects to listings database
- Uses `listingsPool` connection pool for efficient cross-database queries
- Enriches cart items with listing metadata before returning to frontend
- Graceful fallback to metadata if listing fetch fails

### Performance Considerations
- Cart GET endpoint performs one additional query per item to fetch listing details
- Consider caching listing details if cart contains many items
- Index on catalog_id ensures fast lookups
- Frontend uses lazy loading for images and optimistic updates
