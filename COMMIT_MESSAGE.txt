## 2026-03: Transport Hardening V4 — strict QUIC validation, macOS-proof capture, H3 fallback detection

### Strict H3 enforcement (no silent fallback)
- **STRICT_H3=1** in k6: when set, any H3 request that does not negotiate HTTP/3 (or status ≠ 200) **throws** and fails the iteration. Threshold `errors: rate<0.01` added so the run fails if fallback occurs.
- **scripts/k6-chaos-test.js**: In `h3_request()`, if `STRICT_H3=1` and `res.proto` is not `"HTTP/3"`, throw. No more logging-only mismatch.
- **scripts/load/k6-http3-complete.js**: Uses actual `result.proto` from extension; when `STRICT_H3=1`, throw if status ≠ 200 or proto is not HTTP/3. Same errors threshold.

### Capture redesign (macOS-proof)
- **Node-only by default on Colima:** When `colima` is available, **CAPTURE_NODE_ONLY=1** is set so L2/L3 (kubectl exec tcpdump) are skipped — avoids macOS killing pipe processes (SIGKILL) and empty pcaps.
- **Ring buffer:** **CAPTURE_RING_BUFFER=1** (default) uses tcpdump `-C 100 -W 5` on the node to prevent OOM; rotated files are copied and merged with mergecap.
- **SIGINT-only stop:** Node capture is stopped with **kill -INT** and up to 10s wait; **no kill -9** so tcpdump can flush. Partial pcap copied if it does not exit.
- **scripts/lib/packet-capture-v2.sh**: L2/L3 gated by `CAPTURE_NODE_ONLY!=1`; ring-buffer copy/merge from VM; strict validation hooks.

### QUIC presence and ALPN guards
- **STRICT_QUIC_VALIDATION=1**: After capture, if no QUIC packets in node pcap or no **h3** ALPN in QUIC TLS → harness **exit 1**. Implemented in `stop_and_analyze_captures_v2()`.

- **docs/TRANSPORT_HARDENING_V4.md**: Full spec — why H3 falls back in Colima (NAT exhaustion, curl vs k6), strict validation, capture redesign, caddy-h3 UDP 443 check, quick reference.
- Env: `CAPTURE_NODE_ONLY`, `CAPTURE_RING_BUFFER`, `STRICT_QUIC_VALIDATION`, `STRICT_H3`.

## 2026-02: k3d API HA, Rotation Suite Exit 107, jslib Option, Preflight Visibility, Infra/Observability Alignment

### Summary and justification
- **Goal:** Reliable preflight on k3d (no indefinite hangs), rotation suite that completes (no exit 107), optional jslib for k6 when egress exists, and clear visibility so failures are debuggable. Align infra (Terraform, Ansible, Chef/Jenkins per ADR), observability (Prometheus, Grafana, Jaeger, OpenTelemetry, New Relic, Splunk, Linkerd, Istio), and MetalLB verification with strict TLS/mTLS and HTTP/1.1, 2, 3 proof.
- **Why:** Preflight was stalling at “Ensuring API server ready” and at “k3d API stabilize” with no visible cause; rotation chaos job exited 107 (script exception) due to remote jslib import in-cluster; k3d API often failed after node restart due to stale kubeconfig. Fixes address root causes without masking failures.

### API server and ensure-api-server-ready.sh
- **Initial block timeout:** The “Checking API server (kubeconfig + optional localhost→127.0.0.1 fix)” block runs in a subshell with a **60s cap** (`ENSURE_INITIAL_CAP`). Prevents hang on `kubectl config view` or `_one_attempt` before the main wait loop.
- **Progress:** Message “Checking API server…” printed immediately after preflight so the script never appears stuck with no output.
- **Timeout on initial fix:** If the cap is hit, script prints “Initial API check timed out after 60s; continuing to wait loop” and proceeds to the main API wait loop (with per-attempt timeout and diagnostics).
- **Post-restart wait:** When `K3D_AUTO_RESTART=1` and the API check fails, after `k3d cluster start` the script now waits **60s** (`K3D_POST_RESTART_WAIT`) before retrying so k3s/etcd have time to come up (HA: one restart should suffice).
- **Diagnostics:** On failure, “What’s going on” shows API server URL, TCP reachability, and suggests 127.0.0.1 when TCP OK but kubectl fails (TLS/SNI).

### k3d cluster create (one-time tuning and HA)
- **TLS SANs:** `scripts/k3d-create-2-node-cluster.sh` now passes `--tls-san=127.0.0.1` and `--tls-san=localhost` to k3s so the API server cert is valid for host access with strict TLS (no x509 after restart).
- **etcd:** Added `--etcd-arg=quota-backend-bytes=8589934592` and `--etcd-arg=max-request-bytes=1572864` (same as Colima stabilization) for stability under load.
- **Docs:** `docs/PLATFORM_CLUSTER_AND_METALLB_AI_HANDOFF.md` and `scripts/K3D_API_HA_AND_TLS.md` (when created) describe one-time tuning and worst-case restart behavior.

### k3d API stabilize (3c0b) — visibility and root cause
- **Kubeconfig refresh:** At start of 3c0b run **`k3d kubeconfig merge <cluster>`** and **preflight-fix-kubeconfig.sh** so we use the current API port after node restart. Every **60s** during the wait, re-run **`k3d kubeconfig merge`** so we pick up the port once the serverlb is ready.
- **Last error shown:** When progress is printed and the last `kubectl get nodes` was FAIL, the script captures and prints the **last error** (stderr) so we see connection refused, x509, timeout, etc. On final failure, the same error and a one-line “→ k3d kubeconfig merge …; kubectl get nodes; or ensure-api-server-ready.sh” are printed.

## 2026-02: Major Overhaul — Colima/k3s, Preflight & Test Rationale, Tech Stack Justification, Hygiene

### Colima + k3s (Kind retired); Docker Desktop and 256 GB wedge
- **Decision**: Record Platform local dev and test pipelines now target **Colima with k3s** as the supported Kubernetes cluster. **Kind is retired** as the default/supported path.
- **Why we moved**: (1) **Docker Desktop limitations** — The embedded Linux VM and storage layer became a single point of failure under sustained load (8 Postgres, Kafka, Redis, K8s control plane and workloads). API server timeouts, TLS handshake timeouts, and “cluster unreachable” were common when Kind ran on top of Docker Desktop. (2) **Storage/metadata wedge at ~256 GB** — At large Docker disk usage (~256 GB or unbounded metadata/overlay), Docker Desktop’s VM could **wedge**: daemon unresponsive, builds and runs hanging, host disk pressure. Kind-based dev and long-running test suites (preflight + 8 suites + pgbench) became unreliable or impossible without a full Docker reset. (3) **Colima + k3s** — Colima provisions a Lima VM with containerd and k3s; API server at 127.0.0.1:6443. Preflight scripts require Colima context by default (`REQUIRE_COLIMA=1`). Secret updates may use `colima ssh kubectl` when the host cannot reach 127.0.0.1:6443 (Runbook).
