## 2026-02: Major Overhaul — Colima/k3s, Preflight & Test Rationale, Tech Stack Justification, Hygiene

### Colima + k3s (Kind retired); Docker Desktop and 256 GB wedge
- **Decision**: Record Platform local dev and test pipelines now target **Colima with k3s** as the supported Kubernetes cluster. **Kind is retired** as the default/supported path.
- **Why we moved**: (1) **Docker Desktop limitations** — The embedded Linux VM and storage layer became a single point of failure under sustained load (8 Postgres, Kafka, Redis, K8s control plane and workloads). API server timeouts, TLS handshake timeouts, and “cluster unreachable” were common when Kind ran on top of Docker Desktop. (2) **Storage/metadata wedge at ~256 GB** — At large Docker disk usage (~256 GB or unbounded metadata/overlay), Docker Desktop’s VM could **wedge**: daemon unresponsive, builds and runs hanging, host disk pressure. Kind-based dev and long-running test suites (preflight + 8 suites + pgbench) became unreliable or impossible without a full Docker reset. (3) **Colima + k3s** — Colima provisions a Lima VM with containerd and k3s; API server at 127.0.0.1:6443. Preflight scripts require Colima context by default (`REQUIRE_COLIMA=1`). Secret updates may use `colima ssh kubectl` when the host cannot reach 127.0.0.1:6443 (Runbook).
- **Hygiene**: Single supported path (Colima + k3s) avoids accidental runs against a stale or wrong cluster; preflight trims completed pods and does aggressive ReplicaSet cleanup to keep the API server responsive.

### Preflight pipeline and test-suite rationale (documented in ENGINEERING.md)
- **run-preflight-scale-and-all-suites.sh**: Documented **in depth** in ENGINEERING.md — every step (0–7) explained: kill stale (0), Colima context + trim (1), preflight kubeconfig (2), API server ready (3), reissue CA/leaf + Kafka SSL + Postgres + social migrations + remove in-cluster K/ZK/PG + patch kafka-external + restart Kafka consumers (3a–3f), scale to baseline (4), re-ensure API + verify Caddy strict TLS (4c–4d), strict TLS/mTLS preflight + CA at repo root (5), pod/DB/Redis + cleanup + wait for ready + optional pgbench (6), run all suites + optional k6 (7). - **Why eight suites**: ENGINEERING now has a table of all eight suites (auth, baseline, enhanced, adversarial, rotation, standalone-capture, tls-mtls, social) with the script and **why we need each one**. One “e2e” cannot cover multi-protocol (HTTP/2, HTTP/3, gRPC), strict TLS/mTLS, zero-downtime rotation, wire-level proof, and 8 DBs; splitting gives clear failure scope and allows optional k6/pgbench without re-running everything.

- **Root cause**: k6 run locally does not trust the dev-root CA that signed record.local; without SSL_CERT_FILE, all requests fail with x509 not trusted.

### API Gateway req.path Fix (Runbook #43)
- **Bug**: URL-rewrite middleware set `(req as any).path` and `(req as any).originalUrl`; Express/Node treat these as read-only getters → `TypeError: Cannot set property path of #<IncomingMessage> which has only a getter` → 500 on auth, gateway healthz, listings healthz.
- **Fix**: Only set `(req as any).url = newUrl`; Express derives `req.path` from `req.url`. See `services/api-gateway/src/server.ts` "API Prefix Middleware".

### Social Suite Known Failures (Runbook #45) + Logging
